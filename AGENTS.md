# DeDato — правила для Codex и Cursor

Каноническая база проекта — [Knowledge/README.md](Knowledge/README.md).
Поддержание её актуальности входит в обычную задачу разработки без отдельного
промпта владельца. Явные ограничения текущего запроса (например, read-only или
запрет менять документацию) имеют приоритет; в таком случае только укажи нужную правку.

## Начало задачи

1. В начале каждой новой сессии, до ответа по существу или изменения файлов,
   **полностью прочитай оба файла**: `Knowledge/README.md` и `Knowledge/onboarding.md`.
   Это обязательный вход и для короткого вопроса, и для знакомой рабочей копии.
   Используй чтение файлов от первой до последней строки. Поиск (`rg`/Grep),
   snippets, первые N строк, ссылки и память предыдущего чата не заменяют чтение.
   Если вывод обрезан, дочитай оставшиеся диапазоны до конца. При ошибке доступа
   не утверждай, что файл прочитан: сообщи конкретное ограничение.
   После успешного чтения кратко отметь в рабочем сообщении оба пути; это
   подтверждение результата чтения, а не замена вызовов инструмента.
2. По реестру выбери 1–3 относящихся к задаче living-документа и прочитай нужные
   разделы; расширяй по необходимости. Не загружай всю базу или архивы.
   В той же сессии уже прочитанное повторяй только при изменении источника,
   цели или потере контекста. Перед изменениями проверь `git status --short --branch`
   и относящийся к задаче diff, включая новые файлы. Сохраняй чужие и ранее
   незакоммиченные изменения.
3. Проверь релевантные утверждения по коду, конфигурации, моделям и тестам.
   Код описывает текущую реализацию; утверждённое требование — ожидаемое поведение.
   При расхождении не подменяй требование дефектом реализации, укажи противоречие.
4. Для локальной web-проверки следуй [локальному процессу](Knowledge/local-development.md):
   `python3 scripts/dev/local.py start` (для агента — `start --no-open`),
   текущий адрес — `status`, остановка — `stop`. Не подбирай порты вручную и
   не запускай второй stack. Постоянную локальную БД не используй для reset/E2E.
   Если запускателя нет, сообщи о несовпадении рабочей копии; не создавай его дубликат.

## Во время работы и перед завершением

1. Сопоставь итоговый diff своей задачи с документацией. Если изменились поведение
   продукта, API, данные, архитектурные границы, конфигурация, команды запуска,
   проверки или эксплуатационный процесс — обнови соответствующий существующий
   living-документ в `Knowledge/` в рамках этой же задачи. Отдельное согласование
   обычной синхронизации документации не требуется. Не откладывай её на отдельный
   промпт и не заменяй обновление предложением «могу обновить документацию».
   Перед финальным ответом проверь фактический diff владельца знания: новый
   документируемый контракт должен быть записан, а устаревшее описание исправлено.
2. Сохраняй плоскую структуру, metadata и владельцев фактов из реестра. Один факт —
   один основной документ; в остальных давай ссылки. Новый документ нужен только
   для предмета без владельца, с добавлением в реестр. Не переписывай retro как
   актуальную инструкцию и не делай общий аудит всей базы ради небольшой правки.
3. Записывай подтверждённый результат и ссылки на исполняемые источники. Различай
   `CONFIRMED`, `REPORTED`, `INFERRED`, `UNKNOWN`. Дату `last_verified` меняй только
   для действительно проверенной области; при частичной проверке обозначь раздел
   и дату отдельно. Локальная проверка не доказывает CI, merge или состояние сервера.
   Не переноси в базу секреты, токены, runtime state, персональные данные и полные логи.
4. Косметические правки, рефакторинг без изменения документируемого поведения и
   задачи только на чтение не требуют формального изменения Knowledge. Не добавляй
   пустые записи, даты или отчёты ради выполнения правила.
5. Выбирай проверки по [testing strategy](Knowledge/testing-strategy.md).
   Для изменённой документации проверь относительные ссылки, anchors, пути источников
   и `git diff --check`. Чужие ошибки и изменения отделяй от результата своей задачи.
6. В финальном ответе кратко укажи `Knowledge: обновлены <пути>` либо
   `Knowledge: обновление не требуется — <причина>`. Если обновление ограничено
   запросом или доступом, назови конкретный документ и оставшееся действие.

Эти правила не разрешают сами по себе commit/push/merge, deploy, миграции,
сброс данных или операции с production/staging. Следуй объёму текущего поручения.
